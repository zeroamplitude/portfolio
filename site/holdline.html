Case study Holdline Proof of concept

One voice agent, five calls, and one last seat.

What happens when one voice agent calls five passengers at the same time, and two of them ask for the last seat on the same flight?

Holdline is a proof of concept, not a product: a fictional airline and fictional passengers, built to find out how far ElevenLabs Agents can be pushed in one believable scenario, and which guarantees have to live outside the model. I did the concept, the agent design, the backend, the presentation layer and the 4:47 narrated demo of a real live run below.

Where does the agent stop and the system start?

01

Most voice-agent demos are one call with one person. The interesting failures show up when many calls share something real, like seat inventory.

The scenario: a fictional airline, Air Eleven, cancels the 4:00 PM from Toronto to Vancouver. Five passengers need rebooking onto two later flights, a 6:00 PM with very few seats and a 7:40 PM with five. One agent, Airy, calls all five at once. Each passenger tests a different capability.

Sophie

Understand

Prefers French. Can the same agent switch language mid-call without a separate queue?

Priya

Help

Needs wheelchair assistance. Can the agent verify her, hold a seat and hand over to a specialist agent without her repeating herself?

Marcus

Know

Angry, and wants cash and an upgrade. Do guardrails hold, and can live CRM context make the answer personal?

Maya and Daniel

Coordinate

Both want the last 6:00 PM seat. Can two independent conversations share one source of truth with zero double bookings?

No humans on the line

02

A live test needs someone to pick up the phone. Instead, each passenger is an ElevenLabs agent too, with its own persona prompt, voice and Twilio number. Airy dials real phone numbers and talks to other agents over the public phone network. Nobody is on any call, so I could rerun the whole scenario as often as I wanted.

The rule I kept from day one: the model is never the source of truth for inventory. Airy can only promise what a small FastAPI and SQLite service grants through webhook tools. The agent decides how to talk. The service decides who gets the seat.

Agent testing, evaluation criteria

Same call, her language

03 · Understand

Airy opens in English. Sophie answers in French. The agent detects the language and carries on in French in the same call, including the identity check where she spells her surname letter by letter.

Worked
Language switching mid-call was reliable once detection was on for the agent.
Friction
Spelled letters (“T comme Thérèse”) are where speech recognition struggles most. It took prompt changes for the spelling to survive, and masking so booking codes never reached the screen.

She said it once

04 · Help

Priya mentions her wheelchair once. Airy verifies her, holds the 6:00 PM and transfers the call to a separate Accessibility Agent. The specialist greets her by name and already knows the seat and the need.

Worked
Agent-to-agent transfer kept the call and the context in one place.
Friction
The transfer replaces the first agent immediately. In the word timestamps, the specialist’s “Hi Priya” started 0.1 s after Airy’s last words, cutting off Airy’s goodbye. A longer transfer delay fixed it.

Policy held. He still said yes.

05 · Know

Marcus has a wedding tomorrow and wants cash compensation and a free business upgrade. Guardrails stop Airy from promising either. Airy logs the request for customer care, then reads his profile from Salesforce over MCP and offers a window seat, his saved preference.

Worked
Platform guardrails plus prompt rules (no upgrades, no rebates, prompt-injection resistance) held under pressure. The MCP lookup ran while Airy kept talking.
Lesson
Refusing is easy. Refusing and still closing the call needs real context, and that came from the CRM, not the prompt.

One seat, one promise

06 · Coordinate

This is the core of the proof of concept. Maya and Daniel are on separate calls and both ask for the 6:00 PM. Neither conversation knows about the other. Both agents call hold_seat. One conditional SQL UPDATE decides, so only one request can ever take the seat.

  1. maya hold_seat AE458 6:00 PM → held 1 → 0 seats
  2. daniel hold_seat AE458 6:00 PM → sold_out
  3. daniel hold_seat AE460 7:40 PM → held same call
  4. maya confirm_rebooking → confirmed
Worked
The agent handled sold_out gracefully and pivoted in the same breath. Sold out is shown as protection working, not as an error.
Proof
A test fires 50 threads at one seat, five rounds: exactly one hold every time. A deliberately naive read-then-write version runs through the same harness and must over-grant, which proves the race is real.

Configuration as code

07 · Under the hood

Every prompt, tool schema and agent setting lives in the repository and is pushed to ElevenLabs by a sync script, so a prompt change is a reviewed diff with tests, not a click in a dashboard. The demo ends in the real ElevenLabs workspace to show that what you saw is what is configured.

What I learned

09 · Findings

Put guarantees in code, conversation in the agent.

The agent is very good at the human part: tone, language, recovering from “sold out”. It should never be the thing that decides scarce resources. Tools that return a decision, idempotently, made the agent’s job simpler.

Agents testing agents is the unlock.

Persona agents on real phone numbers turned a hard-to-test system into one I could rerun on demand. Agent tests in simulation caught prompt regressions before any call minutes were spent.

Live calls never run on a fixed clock.

Calls connect seconds apart and every conversation takes a different path. The presentation had to follow events from the calls, not a script, and skip a beat that didn’t happen instead of faking it.

The details live in the audio.

Spelled names, a brand name read as “Air 11”, a goodbye cut off by a transfer. Most fixes came from reading word-level timestamps, not from changing the model.

What this is not

10 · Scope

Holdline is a proof of concept, not an airline product. The airline, passengers and flights are fictional, and the inventory service is a stand-in for a real reservation system. Taking it further would mean Postgres instead of SQLite, batch calling with a priority engine (connection risk, fare class, loyalty), staged agent versions, and real operator authentication.

Screens are captured from the demo page replaying a recorded run of all five calls, which is how the demo is rehearsed without placing new calls. In the live take shown in the video, the race went the other way: Daniel won the seat and Maya moved to the 7:40 PM.
